## 主要问题 1：`move` 默认值会破坏可重复运行

`prepare_processed_data.py` 默认 `--mode move`，也就是把 raw 目录移动到 processed。代码里 `_transfer()` 在 `mode == "move"` 时直接 `shutil.move`。

这会带来两个问题：

第一，**脚本不幂等**。你第一次运行成功后，raw 目录里的图片已经被移动走了；第二次再运行，源路径就没了。真实合作项目里，数据处理脚本最好能反复跑，尤其是组员环境不一样时。

第二，当前代码里有一个实际 bug：你先把 test groundtruth 从 raw 移动到 processed，然后又在 `build_testset_metadata()` 里从原 raw 位置读取 groundtruth。代码顺序是先 `_transfer(test_gt_src, dst_test_dir / "groundtruth.csv", mode=args.mode)`，然后调用 `build_testset_metadata(src_testset_dir, dst_test_dir, ...)`。 但 `build_testset_metadata()` 里面读取的是 `src_testset_dir / "ISIC2018_Task3_Test_GroundTruth.csv"`。

所以如果用默认 `--mode move`，这里很可能会因为 groundtruth 已被移动而失败。

**建议：默认改成 `copy`。**
对于课程项目，不要为了省空间牺牲可复现性。可以保留 `move`，但不要默认用它。

```bash
python scripts/dataprocess/prepare_processed_data.py --mode copy --force
```

## 真实合作 DL 项目的数据流程通常怎么做

一般会分成这几层：

```text
raw data
  ↓
extracted / staged data
  ↓
processed canonical dataset
  ↓
splits / metadata
  ↓
Dataset + DataLoader
  ↓
training / evaluation
````

对应到你这个项目，我建议是：

```text
data/
├── raw/
│   └── _downloads/              # 原始 zip、kagglehub 缓存，不进 git
├── extracted/                   # 解压后的原始结构，不进 git
├── processed/                   # 项目统一格式，不进 git
│   ├── ham10000/
│   │   ├── images/
│   │   └── metadata.csv
│   └── testset/
│       ├── images/
│       ├── groundtruth.csv
│       ├── metadata.csv
│       └── missing_images.txt
└── splits/                      # 可以进 git，小 CSV
    ├── train.csv
    ├── val.csv
    └── test.csv
```

核心原则是：

**raw 永远不要被修改。processed 可以删除重建。splits 要固定并可追踪。Dataset 只读 processed/splits，不负责下载、解压、清洗。**

你现在已经在往这个方向走，只是中间的 `raw/_downloads/ham10000_kaggle` 同时承担了“下载缓存”和“解压目录”的职责，所以开始显乱。可以把解压结果单独放到 `data/extracted/`，清晰很多。

这个现在会导致训练、评估和测试直接失败。

你的 `model_factory.py` 目前是这样：

```python
def build_model(config: dict):
    model_cfg = config["model"]
    name = model_cfg["name"].lower()
```

也就是说它期待传入的是完整 config，并且 config 里有嵌套的 `model.name`。

但是你的训练脚本现在这样调用：

```python
model = build_model(config["model"], num_classes=NUM_CLASSES)
```

`config["model"]` 在 main 的 YAML 里只是字符串，比如 `"resnet18"` 或 `"baseline_cnn"`。而且还额外传了 `num_classes`。

测试文件也是这样写的：

```python
model = build_model("baseline_cnn", num_classes=NUM_CLASSES)
model = build_model("resnet18", num_classes=NUM_CLASSES)
```



所以现在 main 上跑：

```bash
python scripts/train_baseline.py
```

或者：

```bash
pytest
```

大概率会直接报：

```text
TypeError: build_model() got an unexpected keyword argument 'num_classes'
```

### 建议修法

既然你现在 config 已经改成了简洁格式：

```yaml
model: resnet18
```

那就把 `model_factory.py` 改成兼容这个接口：

```python
def build_model(
    model_name: str,
    *,
    num_classes: int = 7,
    pretrained: bool = True,
    freeze_backbone: bool = False,
):
    name = str(model_name).lower()

    if name == "baseline_cnn":
        return BaselineCNN(num_classes=num_classes)

    if name == "resnet18":
        return build_resnet18(
            num_classes=num_classes,
            pretrained=pretrained,
            freeze_backbone=freeze_backbone,
        )

    raise ValueError(f"Unknown model name: {name}")
```

然后 `train_transfer.py` 里可以这样：

```python
model = build_model(
    config["model"],
    num_classes=NUM_CLASSES,
    pretrained=True,
    freeze_backbone=False,
)
```

baseline 就：

```python
model = build_model(config["model"], num_classes=NUM_CLASSES)
```

这是当前最优先要修的。

## 4. 第二个会报错的问题：Grad-CAM target layer 写错了

`run_gradcam.py` 里现在写的是：

```python
target_layer = model.backbone.layer4[-1]
```



但是你的 `build_resnet18()` 返回的是 torchvision 的标准 ResNet18：

```python
model = models.resnet18(weights=weights)
model.fc = nn.Linear(in_features, num_classes)
return model
```

这个 model 没有 `backbone` 属性，只有 `layer1 / layer2 / layer3 / layer4 / fc`。

所以 Grad-CAM 会报：

```text
AttributeError: 'ResNet' object has no attribute 'backbone'
```

### 建议修法

把：

```python
target_layer = model.backbone.layer4[-1]
```

改成：

```python
target_layer = model.layer4[-1]
```

如果后面支持更多模型，再写一个 helper：

```python
def get_target_layer(model, model_name):
    if model_name == "resnet18":
        return model.layer4[-1]
    raise ValueError(f"Grad-CAM target layer not defined for {model_name}")
```

## 5. 最大的科学性问题：当前 train/val split 有 lesion leakage

你现在已经把 `train.csv` 和 `val.csv` 提交到了 `data/splits/`，这本身是好的。问题是：**当前 split 是 image-level stratified split，不是 lesion-level split。**

`split.py` 现在用的是：

```python
train_test_split(
    df,
    test_size=val_size,
    random_state=seed,
    stratify=df[label_col],
)
```

这只保证 label 分布相对一致，但没有阻止同一个 `lesion_id` 同时出现在 train 和 val。

而我已经在你提交的 CSV 里看到明显泄漏。例如：

`train.csv` 里有：

```text
HAM_0000118
HAM_0002730
HAM_0002761
HAM_0005132
```



`val.csv` 里也有：

```text
HAM_0000118
HAM_0002730
HAM_0002761
HAM_0005132
```



这意味着同一个皮肤病灶的不同图片被分到了 train 和 val。模型可能不是学会泛化，而是在 validation 里见到了高度相似的病灶样本，导致 validation score 偏高。

### 建议修法

短期至少做一个检查：

```python
train_lesions = set(train_df["lesion_id"])
val_lesions = set(val_df["lesion_id"])
overlap = train_lesions & val_lesions
print(len(overlap))
```

更好的做法是把 `create_splits()` 改成 group-aware split。

推荐优先级：

1. **最好**：`StratifiedGroupKFold`
2. **次好**：`GroupShuffleSplit`，按 `lesion_id` 分组，但 label 分布可能不如 stratified
3. **最低限度**：保留当前 stratified split，但在报告里承认 limitation

我建议你不要保留现在这版 `data/splits/train.csv` 和 `val.csv`，应该修完 split 逻辑后重新生成并提交。
